\chapter{Research Methodology and Evaluation Framework}\label{ch03}

This chapter states how the research was carried out and how every result in Chapters~\ref{ch05}
and~\ref{ch07} was measured. It defines the datasets, the reference answers, the two ways an answer is
scored, the metrics with their denominators, and the statistical tests. These are defined once here, so
that the evaluation chapters can concentrate on what was found.

\section{Research Approach}\label{sec:ch03-research-approach}

The work follows a design-science approach~\cite{hevner2004design}: an artefact (the knowledge-graph
builder and the query engine) is built to address a practical problem, and its design is justified by
evaluating it rather than by argument alone. Three choices give this general approach its specific form.

\paragraph{Small, measured steps.} The system was developed in a sequence of numbered steps (R0 to R231 in
the project roadmap). Each step addressed one concern, ended in runnable and tested code, and was recorded
with its commit, its cost and the measurements it made. The step identifiers are used throughout this thesis
as experiment identifiers; \cref{app:complete-result-tables} maps each one to its records.

\paragraph{Alternatives as parallel arms.} When a design question could not be settled by reasoning, the
alternatives were built as separate arms on their own version-control branches and measured against each
other on the same inputs. The graph representation went through four such arms (\cref{sec:ch04-evolution});
the retrieval and query components through several more (\cref{sec:ch07-retrieval-components}).
Because each arm is preserved on its branch, every comparison can be re-run from the code that produced it.

\paragraph{Decision rules fixed before measuring.} Where a measurement decided between designs, the rule
that would decide was written down before the measurement was made. Three examples recur in later chapters.
The pass thresholds of the builder's audit criteria C0--C9 were fixed in the design document before the
first audit~(\cref{sec:ch05-method}). The choice of the agent's start-node seeding
was made by a rule chosen before the grid of candidate settings was scored~(\cref{sec:ch07-retrieval-components}).
The adoption of a combined agent variant required, in advance, that it lose no question the baseline
answered; it did lose one, and it was not adopted~(\cref{sec:ch07-targeted-ablations}). Fixing the rule
first protects a small study from the most common error of iterative development: choosing, after the
fact, the reading of the numbers that favours the newest change.

\paragraph{Paired comparisons.} Whenever two designs could be run on the same questions, they were compared
question by question rather than by their overall rates (\cref{sec:ch03-statistical-analysis}). With the
small samples available here, two overlapping confidence intervals rarely decide anything, while the
handful of questions on which two systems disagree often does.

\section{System Overview}\label{sec:ch03-system-overview}

\Cref{fig:system-overview} shows the system as a whole. It has two subsystems that share three stores.

\begin{sidewaysfigure}
\centering
\includegraphics[width=\linewidth]{diagrams/system/r0_r231/r231_diag1_system_architecture.pdf}
\caption{Overall architecture of the final system. Orange rounded boxes are steps where a language model
proposes; square boxes are deterministic code (blue: the query agent's tools); cylinders are stores. Stage names
are the commands of the \texttt{kg} tool.}
\label{fig:system-overview}
\end{sidewaysfigure}

\paragraph{The builder} (\cref{ch04}) reads a folder of mixed sources. A language model proposes a plan that
maps each table to node labels, keys and relations; code validates the plan and imports the rows into a Neo4j
graph. The text is split into chunks, embedded, and indexed. A second proposal names the kinds of facts the
text holds; a model extracts them, and the mentions of things in the text, with quotes that code verifies.
Code and, for the uncertain cases only, a model then decide which mentions refer to which records and to
each other. The result is an \emph{anchor graph}: an index that leads from the things a question is about
to the records and passages that concern them.

\paragraph{The query engine} (\cref{ch06}) answers a question with an agent: a language model that calls
read-only tools one at a time --- graph navigation, passage search, and typed queries over the records and
tables --- and finally answers with citations to what the tools returned. A deterministic screen in front
of the agent refuses requests to change the data, and code checks every citation and the form of every
answer before it is returned.

\paragraph{The stores.} Neo4j holds the graph and its vector and full-text indexes; DuckDB holds the
tables for structured queries; MLflow records every stage and every model call.

\paragraph{A fifth dataset, excluded.} A fifth dataset was built and measured with the same code and the same
rules: encyclopaedia articles about lighthouses with tables of open structured data on the same lighthouses. It
is excluded from the results of this thesis. The criterion, its timing and the effect of the exclusion are
stated here so that the reader can judge the decision.
\begin{itemize}[nosep]
\item \emph{The criterion.} The builder's audit criterion C4 requires that at least 95\,\% of the links from
text mentions to records be right (\cref{sec:ch05-method}). This bound was fixed in the builder's design
document on 6~October~2026, before the fifth dataset existed.
\item \emph{The measurement.} The dataset was built on 12~October and its graph audited on 16~October 2026:
34 of 36 links were right (94.4\,\%, Wilson interval 81.9--98.5\,\%), below the bound. In both wrong links the
generic word ``lighthouse'' was linked to the article's own lighthouse where the sentence meant another one.
\item \emph{The decision.} The decision to exclude a dataset whose graph fails a hard gate, rather than to
report it beside the others, was taken after this measurement, on 16~October 2026, when the builder was frozen
for the thesis. It is therefore a post-hoc decision applying a pre-defined criterion, not a rule fixed in
advance.
\item \emph{Its effect.} On the builder's results, the exclusion removes the only dataset that fails an audit
gate; the four reported datasets pass every gate, and this must not be read as evidence that the builder passes
on every dataset it was measured on. On question answering the effect is mixed: by meaning, the excluded
dataset scored below the average of the other four on two question sets and above it on two.
\end{itemize}
Every measurement of the excluded dataset is listed in \cref{app:excluded-dataset}, and its records remain in
the project repository.

\paragraph{Scale.} All four datasets are small: tens of documents and at most a few hundred rows each. This
was deliberate --- every judged number in the thesis required reading the sources in full --- but it limits
what the results say about larger corpora (\cref{sec:ch08-threats-to-validity}).

\section{Ground Truth}\label{sec:ch03-ground-truth}

\paragraph{Who wrote it.} No human-labelled reference exists for these datasets, and labelling one by hand
was not feasible in the time available. All reference data (\emph{gold}) was therefore written by a strong
language model from a different family than the system under test: Claude (Opus~5.5 for most sets, Fable~5.1
and Sonnet~5.5 for some later ones), while the system itself uses Gemini models. This is a limitation stated
wherever a number depends on it. Three rules reduce its effect.

\begin{enumerate}[nosep]
\item \emph{Gold before output.} Each gold set was written from the source files only, before any output of
the system for those files was opened.
\item \emph{Verbatim evidence.} Every gold item carries the sentence that supports it, copied verbatim; an
automated test fails if a quote is not found in its document, a record is not in its table, or the answer to
a structured question differs from the answer DuckDB computes from the tables.
\item \emph{Recorded corrections.} A gold item changed after output was seen is a \emph{gold correction}; it
is allowed, since the writer can be wrong, but it is listed with its reason in the step that made it.
\end{enumerate}

\paragraph{Builder gold.} The builder is measured against several references, each described with its
experiment in \cref{ch05}: the claims a careful reader lists for 40 randomly chosen sentences per dataset; the
mentions of things in the same sentences; pairs of names that do or do not refer to the same thing; and, for
each question, the names it starts from, the records it should reach and its evidence chunks.

\paragraph{Question gold.} The question sets used in \cref{ch07} are listed in \cref{tab:question-sets}. The
benchmark questions were written after the query engine was frozen, and each confirmation set before the
fixes it was meant to confirm existed; their writers opened no output, verdict or failure analysis. Each file
was then reviewed twice by independent reviewers, who re-derived every answer from the sources, re-ran every
structured query and checked that no question repeated a fact asked before, and corrected in a third pass.

\section{Scoring: Exact Match and Judgement by Meaning}\label{sec:ch03-scoring-exact-match-and-judgement}

Every answer and every judged builder output is scored in two ways, and every number in this thesis names
which of the two it is.

\paragraph{Exact match} is computed by code. A set of names is right when it equals the gold set after
normalisation (case, accents and spacing); a number is right when it equals the gold number; a short free-text
answer, which code cannot compare, takes the judge's verdict. Exact match is free, deterministic and
reproducible, but strict about form: ``over 440 miles'' is wrong against the gold number 440.

\paragraph{Judgement by meaning} uses a language model as the judge~\cite{zheng2023judging}. The judge is
Claude, never the Gemini model that built the graph or answered the question, since a model judging its own
output tends to favour its own phrasing. The judge reads the question, the answer, the gold answer and its
evidence, and follows six fixed rules, of which the central one is \emph{content, not form}: an answer is right
when it states what the gold answer states, in any wording, with nothing contradicting the source; an answer
missing a part of the gold answer, or giving only part of a value, is wrong; ``the texts do not say'' is wrong
when the source does say.

\paragraph{The judging protocol.} For question answering, two judges work blind and independently on each
answer file; a third, lead judge resolves their disagreements. On the 250-question benchmark the two blind
judges agreed on every verdict. For builder outputs, one blind judge labels each batch, and the lead reviews
every verdict other than \emph{valid} and a seeded random 10\,\% of the valid ones. Builder verdicts use five
labels: \emph{valid}; \emph{valid alternative} (right, though not as the gold has it); \emph{incorrect};
\emph{ambiguous} (the text honestly supports both readings); and \emph{unjudgeable}. From them three rates are
derived:
\begin{align*}
\text{strict} &= \frac{\#\text{valid}}{n_{\text{decided}}}, \\
\text{accepted} &= \frac{\#\text{valid} + \#\text{valid alternative}}{n_{\text{decided}}}, \\
\text{worst case} &= \frac{\#\text{valid} + \#\text{valid alternative}}{n_{\text{all}}},
\end{align*}
where $n_{\text{decided}}$ excludes ambiguous and unjudgeable items and $n_{\text{all}}$ counts them as wrong.
The accepted rate is reported unless stated otherwise; where the worst case differs, it is given too.

\paragraph{The judge is not ground truth.} Judgement by meaning is lenient about form by design, and the judge
belongs to the same model family as the gold writer. Neither score replaces the other: exact match is a lower
bound that undercounts correct paraphrases, and the judge is an informed reading that may share the gold
writer's blind spots. No agreement figure with a human judge exists (\cref{sec:ch08-threats-to-validity}).

\section{Statistical Analysis}\label{sec:ch03-statistical-analysis}

\paragraph{Confidence intervals.} Every rate is reported as $k/n$ with a 95\,\% Wilson score
interval~\cite{wilson1927probable}, which, unlike the normal approximation, stays within $[0,1]$ and remains
reliable for rates near 0 or 1 and for small $n$ --- both common here. With $\hat p = k/n$ and $z = 1.96$:
\[
\frac{\hat p + \frac{z^2}{2n} \pm z\sqrt{\frac{\hat p(1-\hat p)}{n} + \frac{z^2}{4n^2}}}{1 + \frac{z^2}{n}}.
\]

\paragraph{Paired comparisons.} When systems A and B answer the same questions, only the discordant questions
carry information about which is better: $b$, right only in A, and $c$, right only in B. The exact McNemar
test~\cite{mcnemar1947note,dietterich1998approximate} treats each discordant question as equally likely to
fall either way under the null hypothesis, so $\min(b,c)$ follows a binomial distribution with
$n = b + c$ and probability $\frac12$, and the two-sided p-value is
\[
p = \min\left(1,\; 2\sum_{i=0}^{\min(b,c)} \binom{b+c}{i} 2^{-(b+c)}\right).
\]
The exact form is used rather than the chi-square approximation because a single change typically alters a
handful of questions, where the approximation is unreliable. Results are written ``$b$/$c$, $p$''. The same
test is applied to retrieval outcomes (a question's evidence complete or not) and to builder arms.

\paragraph{Unpaired comparisons.} Different question sets cannot be paired. Accuracy on two such sets is
compared with a two-proportion $z$-test, computed in the analysis of the step concerned. Since the sets differ
in their questions, a difference between them is never attributed to a change in the system; they are read as
repeated measurements of one level.

\paragraph{Significance and its limits.} The significance level is $\alpha = 0.05$. A test whose comparison
was chosen after seeing the data is labelled \emph{exploratory}, and its p-value is reported but not used to
decide. Several experiments were run on sets chosen because the system had failed them; their rates describe
those failures and say nothing about the general error rate. No correction for multiple comparisons is
applied; the number of tests in each experiment is stated instead, so their weight can be judged.

\section{Reproducibility}\label{sec:ch03-reproducibility}

\paragraph{Tracking.} Every stage of every run is an MLflow run, nested under a parent run for a whole pipeline.
Each records its parameters (models, temperature, thinking level, prompt version hash, thresholds, dataset
path), its metrics (counts, rates, latency, tokens, cost) and its output files, and is tagged with the git
commit it ran on and any uncommitted files. The project holds 2{,}566 such runs. Every result in this thesis
names its run; \cref{app:complete-result-tables} lists them.

\paragraph{Records.} Each experiment's inputs and outcomes --- gold files, judges' verdicts, per-question
outcomes and the list of runs --- are committed to the repository under the step's identifier. The figures of
this thesis are drawn by scripts from these committed records only, never from a database or a working
folder, and a test checks that the numbers in each figure equal the records.

\paragraph{Cost-free replay.} Every model response is cached by the exact request. A run repeated with the same
code and inputs is served from the cache at no cost, which is how the graphs were reloaded for every question
set and how several analyses were re-run on recorded data. A content digest of each graph confirms that a
reloaded graph is identical to the one measured.

\paragraph{Cost accounting.} Each model call's tokens are priced from a versioned price table at the providers'
list prices. Embedding calls are not priced, because the embedding service reports no token usage; their cost
is therefore missing from the totals and is stated as such.

\paragraph{Code.} The system is about 36{,}700 lines of Python with about 1{,}185 automated tests, which run
without a network or a paid model (models and databases are replaced by test doubles behind the same
interfaces). \Cref{app:reproducibility-guide} gives the commands to rebuild each graph and repeat each
measurement.

\section{Validity Framework}\label{sec:ch03-validity-framework}

The threats to the validity of the results are examined in \cref{sec:ch08-threats-to-validity}. They fall
into four groups, each with the mitigations described in this chapter:
\begin{itemize}[nosep]
\item \emph{Construct validity} --- whether the metrics measure what is claimed. Two scores, both reported; the
graph evaluated as an index by criteria fixed in advance rather than only through answers.
\item \emph{Internal validity} --- whether an observed difference is caused by the design change. Paired tests,
pre-stated decision rules, arms run on identical inputs.
\item \emph{External validity} --- whether results carry over to other data. Four datasets of different domains
and forms, one of them unseen; limited by their small size.
\item \emph{Conclusion validity} --- whether the statistics support the conclusions. Wilson intervals,
exact tests, exploratory comparisons labelled, single runs stated.
\end{itemize}
The largest single threat is that the gold, the judge and much of the failure analysis come from one model
family. It cannot be removed without human labelling; it is stated with every judged number.
